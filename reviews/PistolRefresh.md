# Исправление выбора оружия после !wp

## Текущий статус: perf.18, ручная приёмка ожидается

Perf.16 прошла один реальный P90 → !wp дважды → новый раунд без вылета, но
владелец подтвердил регрессию: P90 падает на землю и требует подбора. Это **не
принятая сборка**. Проверки одиночных defindex и lone P90 не покрывали полное
обновление сразу ножа, пистолета и основного оружия.

Исправление снимает с игрока именно запланированный предмет: временно назначает
его активным для синхронного native drop, проверяет фактическое отсоединение,
удаляет entity и возвращает прежний активный предмет, если он остался у игрока.
125 проверок с подключённым production helper покрывают все порядки снятия,
каждую активную позицию и отказ native detachment. Последующее восстановление
LastWeapon защищено исходной identity и выбором активного предмета.

Из-за занятости #7 новый кандидат проверяется на пустом #6, выбранном в рамках
разрешения владельца использовать другой пустой сервер. WP config и MenuManager
сохраняются. Временное ограничение входа будет снято перед ручной проверкой.
#7 пока остаётся на perf.16; занятый сервер не перезапускался. PR остаётся draft.

Native fixture дополнена полным обновлением 4 предметов во всех 6 порядках
выдачи, удержанием P90/пистолета/ножа и обновлением пистолета при удержании P90.
Начальная проверка LastWeapon оказалась некорректна: поле задавалось сразу после
GiveNamedItem, а движок менял его ещё до queued refresh. Исправленный fixture
сначала ждёт стабилизации выбора, затем сравнивает фактический LastWeapon.
Native matrix завершена: 24/24 сценария, 2400 запросов; нет потерянных предметов,
оставленных на земле старых entities или invalid inventory handles, сохранены
active/last/ammo/attack и неподменённая дымовая граната. Вход на #6 снова открыт,
исходные gamecfg/runtime восстановлены. Скины бота дают неодинаковые fallback
наблюдения, поэтому реальный клиент проверяет и P90, и пистолет. Приёмка
реального клиента и merge ещё ожидаются. [Evidence](../docs/measurements/p90-20261110/README.md).

## Блокирующий клиентский crash на perf.14 — 10.11.2026

Статус: **rework / client acceptance failed**. PR не готов к merge/выпуску.
Владелец сообщил, что после дополнительной выдачи P90 через админку и попытки
применить скин клиент закрылся с `OnPreserveEntity: missing client entity 322`.

Read-only диагностика установила:

- Сервер не завершался: PID CS2 `4023941` остаётся с запуска perf.14
  (18:19:48 по Саратову), uptime около 36 минут на момент проверки после вылета.
  RCON отвечает, perf.14 и DLL SHA256 совпадают; сервер продолжил обслуживать
  другого подключённого игрока. Новых managed WP warnings/errors — 0.
- В серверном/клиентском журналах: 18:53:43 — `css_give ... P90`, затем `!wp`
  в 18:53:48 и 18:53:51; около первого дампа происходит OnPreResetRound для
  обоих игроков. На стороне сервера видны затем timeout отключившегося клиента,
  full-update retry и предупреждения unresolved controller network offset 72.
  Эти предупреждения не приписаны WeaponPaints без отдельного source/runtime trace.
- Локально найдены два клиентских minidump 18:53:54 и 18:54:39. Проверены CDB
  read-only; оба имеют `Curtime 2031.718750` / `Realtime 94.411522` и одинаковую
  цепочку engine2/networksystem. Это записи одного остановившегося игрового
  состояния, а не два независимых воспроизведения. Последний содержит точный
  AbortMessage с отсутствующей entity 322. Exception 0x80000003 проходит через
  tier0/Plat_FatalError; это deliberate engine fatal, не C# stack trace.
- Клиентский console.log также содержит выбранные кастомные модели оружия.
  Их участие, передачу/скрытие entities другими плагинами и порядок round reset
  пока нельзя исключить. По одному отсутствующему клиентскому entity index
  нельзя восстановить его класс/владельца в момент сбоя; индекс мог переиспользоваться.

Цепочка admin P90 → !wp → round transition является точным новым сценарием.
Причинность удаления/перевыдачи, явного deploy, CustomWeapons или transmit-кода
ещё не изолирована. Unit/bot checks с одиночными предметами не подтверждают
сетевую синхронизацию реального клиента в этом сценарии. Нужен контролируемый
прогон с фиксацией full serial/entity class и lifecycle событий до/после refresh
и round reset, с сопоставимым baseline; не повторять слепую выдачу perf.14 за
готовое исправление.

Сервер/конфиги/плагины при этой диагностике не менялись и не перезапускались.
Raw дампы и приватные журналы не публиковались; локальные выдержки/стек и
результаты — `C:/Users/koiie/.codex/tasks/wp-client-fatal-20261110/`.

## Продолжение perf.14

Владелец подтвердил сохранение патронов на perf.13, но обнаружил пустые руки
после смены paint удерживаемого пистолета до ручного переключения. Поэтому
perf.13 не считается принятым исправлением видимого deploy.

WeaponRefresh восстанавливал native ActiveWeapon для всех предметов, но явный
client holster/deploy выполнял лишь при смене ТИПА активного ножа. Теперь этот
ограниченный путь применяется к любому заменённому удерживаемому rifle/pistol/knife:
через уже имеющееся альтернативное оружие (в приоритете captured LastWeapon),
затем slot1/slot2/slot3 соответствующего целевого предмета. Для одиночного
инвентаря сохранён ограниченный holster state; он восстанавливается при отмене
таймера/cleanup даже если началась новая загрузка данных. Новые предметы ради
переключения не выдаются. Неактивный предмет не отбирает выбор у активного;
ручная смена во время задержки, death/pawn/controller/map/ownership guards сохранены.

Production deploy выделен в WeaponRedeploy.cs, 39 проверок компилируют его
напрямую с engine/client adapters. Пистолет/основное/нож, одиночный инвентарь,
правильный слот возврата, captured last, отмена/cleanup проходят. Вместе с 32
equipment checks, 47 preview checks, 22 pet checks и 28 catalogue tests проходят
Release и CI-ready local checks. Они не доказывают first-person rendering;
нужен повторный тест владельца. Оба дефекта сохраняются открытыми до него.

## Первоначальный отчёт perf.13

10.11.2026. В совместной проверке perf.12 владелец подтвердил превью, перчатки и
удаление шапки курицы, но сообщил: при удержании пистолета `!wp` переключает на нож.
Это уточняет прежнее общее подтверждение работоспособности; дефект открыт до
проверки исправления на реальном клиенте.

В исходном порядке GivePlayerGloves немедленно отправляет `lastinv`, затем
RefreshWeapons на следующем кадре запоминает ActiveWeapon/LastWeapon и начинает
перевыдачу. Через 0.08 с glove callback отправляет второй `lastinv`. Между этими
переключениями изменяются и экземпляры оружия, и captured selection; их нельзя
считать парой относительно одного и того же состояния инвентаря. Кроме того,
ранний выход при отсутствии glove data раньше мог оставить первое переключение
без обратного.

perf.13 вводит общий RefreshPlayerEquipment для `!wp`, server refresh, connect и
hot reload: сначала glove attributes, затем RefreshWeapons, без `lastinv` на этом
пути. Оружие по-прежнему пересоздаётся существующим coalesced refresh, который
сам выполняет deploy. При отсутствии выбранных/включённых перчаток оружие
обновляется сразу. Отдельное меню перчаток сохраняет прежнюю визуальную пару
переключений, причём отсутствие/очистка выбора больше не оставляет её неполной.
Проверки connection/controller/pawn/map сохранены. Нет нового OnTick/сканера,
изменения SQL, команд, пакетов, config или характеристик оружия.

Локально проходят Release build, 32 новых проверки production scheduler,
22 pet checks, 47 preview callback checks, 28 catalogues/57876 rows и проверка
исторических measurements/33 distributions. Сборка со строгими code warnings:
`dotnet build WeaponPaints.csproj -c Release --no-restore -warnaserror -warnnotaserror:NU1902`.
Старый NuGet advisory MySqlConnector 2.5.0 остаётся видимым warning; зависимость
не менялась. Новый suite включён в CI; его engine boundaries описаны в README.

Нужна клиентская приёмка: пистолет в руках → `!wp` без смены оружия; повторить с
основной пушкой/ножом, проверить Q/патроны и смену перчаток через меню, а также
обновление выбранных на сайте перчаток через `!wp`. Нативная геометрия и вид
перчаток после отключения лишних toggles не объявляются доказанными unit tests.
Пока владелец на #7, сервер не обновлялся; candidate готовится для пустого окна.
